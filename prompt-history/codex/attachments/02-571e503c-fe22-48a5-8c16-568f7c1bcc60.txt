The four anomalies. Each passes every foreign key, and only its business meaning is wrong.
1. BALANCE_NOT_RECONCILED: one stored CLOSING value is changed. It’s detected because stored differs from opening plus ledger.
2. RESERVATION_EXCEEDS_AVAILABLE: a new order holds more than was available, and its decision log shows a stale ATP. It’s detected by recalculating at that time without trusting the log.
3. FULFILLED_FROM_BLOCKED: a new order’s SALE draws from the BLOCKED bucket. It’s detected from the SALE row itself.
4. TRANSFER_DOUBLE_COUNTED: a new transfer’s TRANSFER_IN is timed before its TRANSFER_OUT. It’s detected by comparing the two rows on the same shipment.
Each type also gets valid decoy rows that look suspicious. Flagging one counts as a false positive.
1. Reservations at a past time

The reservation row now stores only fixed facts. To find its state at time t, take the latest event at or before t. It holds stock if that state is CONFIRMED, or if it’s ACTIVE and t is before expires_at.

Example: 5 units expiring at 10:30, confirmed at 10:20, cancelled at 11:00.
- At 09:59: holds 0 (it doesn’t exist yet)
- At 10:10: holds 5
- At 10:45: holds 5 (confirmed, so expiry no longer applies)
- At 11:00: holds 0
If it was never confirmed, it holds 5 at 10:29 and 0 at 10:30, even if the expiry job runs late.

2. Damage without increasing total stock

on_hand is sellable plus blocked. A BLOCK always writes two rows: −3 SELLABLE and +3 BLOCKED. They add to zero, so sellable 95 and blocked 5 becomes 92 and 8, and on-hand stays 100. ATP still falls by 3. Only a WRITE_OFF lowers total stock.

One function writes both rows together, and the validator rejects any group that isn’t a matching pair.

3. Orders using incoming stock
- A reservation is either all ON_HAND or all INBOUND, and an INBOUND one names one shipment.
- promised_ship_by is the ETA plus 24 hours.
- It can’t ship until that shipment is RECEIVED. Arrival triggers shipping, oldest reservation first.
- If the ETA passes:
  1. The shipment gets a new ETA event.
  2. The reservation tries another location with stock.
  3. If there’s none, it gets a new promised date, and the first promise stays in history.
  4. Past 3 days late, it’s cancelled and the hold is released.
4. Which rows are locked

The lock is on sku_location, one row per stocked SKU at a location.
1. Begin a transaction at READ COMMITTED.
2. Find the candidate pairs from master data only, reading no stock numbers.
3. Remove duplicates and sort by sku_id, then location_id.
4. Run SELECT ... ORDER BY sku_id, location_id FOR UPDATE.
5. Only then recalculate availability, in new statements.
6. Write everything and commit.
The second order waits at step 4, then sees the first order’s reservation at step 5 and is refused. The fixed sort order prevents deadlocks. If a lock waits over 5 seconds, it rolls back and returns 503.
Every walk-in sale passes qty <= sellable - reserved, or it’s refused and no row is written. Rows already promised are held out of the budget, so optional events can’t use them up.

The final top-up uses the same check. If sales keep being refused, it posts a real warehouse delivery instead. If that also can’t reach the target, the run stops with an error.
